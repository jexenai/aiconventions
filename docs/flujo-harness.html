Para empezar: siete ideas

Si nunca has programado con un agente de IA, estas siete ideas bastan para seguir el resto del documento. Todo lo demás son detalles de cómo la plantilla las aplica.

Agente principal
El asistente de IA con el que conversas y que trabaja en tu repositorio: lee ficheros, escribe código y ejecuta comandos como las pruebas. Aquí, Claude Code. En esta guía, «agente principal» es siempre esa conversación.
Subagente revisor
Otro agente que el agente principal lanza solo si tú lo pides o lo confirmas. Trabaja con su propia ventana, sin ver la conversación: lee el cambio terminado, informa de lo que encuentra y no modifica código.
Ventana de contexto
Todo lo que el agente principal tiene delante en este momento. Lo que no está en la ventana, no lo sabe. Es limitada: cuanto más relleno inútil, peor se concentra. Por eso la plantilla carga cada cosa solo cuando hace falta.
Regla
Una hoja corta de pautas de un lenguaje (PHP, React…). Entra sola en la ventana cuando el agente principal abre un fichero de ese lenguaje. Nadie tiene que acordarse de pedirla.
Skill
Un procedimiento o guía más larga que solo se carga cuando se invoca (/commit) o cuando una regla dice «léela antes de…».
Escenario
Un caso concreto del comportamiento esperado, escrito en lenguaje natural con la forma Dado… Cuando… Entonces…. Es lo que el usuario revisa y aprueba antes de programar.
Pruebas primero (TDD)
Por cada escenario, el agente principal escribe primero una prueba automática, la ve fallar y solo entonces escribe el código que la hace pasar. Así cada escenario queda demostrado, no supuesto.

Las etapas en verde claro son decisiones tuyas: el agente principal propone, pero no avanza sin ti. Las moradas las conduce OpenSpec, la herramienta de especificaciones. El trío rojo, verde y ordenar se repite por cada escenario.

El reparto

Seis actores intervienen en el ciclo y conviene no confundirlos, porque cada uno falla de una manera distinta.

ActorQué haceQué no puede hacer
Harness El programa que envuelve al modelo (Claude Code). Carga CLAUDE.md y las reglas por ruta, aplica permisos y arranca los servidores MCP No interpreta la documentación: no sabe qué dice la ficha
Agente principal La conversación con la que trabajas: lee, decide qué documento abrir, llama a las herramientas, escribe el código y las pruebas, y lanza los subagentes cuando se lo confirmas No puede saltarse un permiso ni aprobar un servidor
Skill Aporta un procedimiento o una guía cuando la tarea coincide No se ejecuta sola: el agente principal o quien desarrolla la invoca
OpenSpec Guarda el comportamiento esperado y entrega al agente principal la guía de pruebas primero No lo define la plantilla: su workflow se instala y manda sobre él
Subagente revisor Un subagente que lanza el agente principal: otro agente, con su propia ventana limpia, que lee el cambio terminado y devuelve un informe No modifica código y no se lanza si el usuario no lo pide o lo confirma
Usuario Pide, revisa los escenarios, decide si pasar subagentes revisores, aprueba servidores y permisos No debería tener que repetir contexto que ya está escrito

La plantilla no inventa ninguno de estos papeles: se limita a dejar escrito, en el sitio donde cada actor ya mira, lo que necesita para no equivocarse.

Fase 0

Adopción del repositorio

una vez

Ocurre al incorporar la plantilla a un proyecto. Deja escrito lo que todas las sesiones posteriores darán por sabido. Las decisiones que se toman aquí —especificaciones, vistas y sistema de diseño— gobiernan el resto del ciclo.

  1. 01
    Usuario

    Elegir el stack

    El plugin genera docs/stack.yaml a partir de una plantilla de templates/. Para este recorrido, laravel10: PHP 8.4 con Laravel en el backend, vistas React 18 en resources/js/ y Oracle 19c como base de datos. Ese archivo es la intención declarada del equipo, no la prueba de lo implementado: todo lo que salga de él se contrasta después con el repositorio.

  2. 02
    Usuario setup-project-context

    Rellenar la ficha con evidencia

    La skill solo arranca cuando el usuario la invoca, y sigue un flujo fijo de seis fases. Primero analiza el repositorio sin tocar nada y prepara una propuesta para cada dato de la ficha: propósito, tecnologías, ruta del código, vistas, comandos de arranque y pruebas, base de datos y sistema de diseño.

    Después plantea siempre el mismo guion de nueve preguntas en tres rondas —ficha, ejecución y OpenSpec—, también al repetir el setup. En laravel10, la pregunta de las vistas ofrece las dos formas de unir Laravel y React que declara el stack: Inertia.js o API REST + SPA. En este recorrido se elige API REST + SPA: Laravel expone endpoints JSON y React los consume. Lo que nadie confirma queda en [POR DEFINIR] en lugar de inventarse.

  3. 03
    Usuario setup-openspec

    Decidir si habrá especificaciones

    Es la tercera ronda del guion, obligatoria y sin opción recomendada: usar OpenSpec es una decisión de equipo, no un dato deducible del repositorio. Si el usuario acepta, la misma ejecución continúa con setup-openspec, que pregunta las herramientas y confirma la instalación antes de instalarlo —una de las dos excepciones a la regla de no instalar dependencias; la otra es setup-testing—.

    Al inicializarlo escribe en openspec/config.yaml la política de pruebas primero. Es lo que, más adelante, hará que cada tarea empiece por la prueba de su escenario sin que nadie tenga que recordarlo.

    # openspec/config.yaml (extracto) rules: tasks: - Toda tarea que cambie comportamiento empieza por la prueba del escenario que cubre, y esa prueba debe fallar antes de implementar. operations: apply: # se entrega al agente principal al programar guidance: [prueba en rojo, mínimo para verde, ordenar, suite del área] archive: # se entrega al agente principal al archivar guidance: [ofrecer los subagentes revisores si nadie lo hizo tras verificar]
  4. 04
    setup-project-context

    Materializar lo que el stack declare y retirar lo que sobra

    laravel10 declara el servidor MCP shadcn, un catálogo de componentes de interfaz. La skill lo añade a .mcp.json sin arrancarlo: configurar un servidor no es activarlo.

    Después retira de .claude/ lo de los stacks que el proyecto no usa. Lo hace con una tabla fija, no con el criterio del agente principal, y al final comprueba que no queda nada. Si la respuesta sobre tecnologías o vistas quedó pendiente, no borra nada.

    El informe del setup lo resume en su sección «Stacks», con una fila por componente: conservado, retirado o pendiente.

  5. 05
    setup-project-context

    Cerrar la ficha

    El resultado son unas pocas filas que el agente principal leerá en cada sesión posterior. No son documentación: son interruptores.

    | Dato | Valor | | Código de aplicación | app/ | | Arrancar en local | Backend: php artisan serve · Vistas: npm run dev | | Pruebas habituales | Backend: php artisan test · Vistas: [POR DEFINIR] | | Capa de vistas | React 18 en resources/js/, API REST + SPA | | Especificaciones | OpenSpec 0.9.2 | | Sistema de diseño | shadcn/ui, servido por shadcn

    Cuando el proyecto tiene dos partes, arranque y pruebas llevan un comando por parte. Las pruebas de las vistas quedan pendientes: el package.json de Laravel solo trae dev y build, y el setup no inventa un npm test que no existe. Su informe recomienda el paso siguiente.

  6. 06
    Usuario setup-testing

    Preparar las pruebas que faltan

    Sin un ejecutor de pruebas en las vistas, el ciclo de pruebas primero se rompe en el frontend: no hay forma de ver fallar la prueba del escenario. setup-testing lo resuelve. Como el resto de los setups, solo arranca cuando el usuario lo invoca.

    Primero anota qué tiene cada parte y qué le falta. Después pregunta en dos rondas qué preparar —vistas, backend, extremo a extremo y la base de datos de pruebas— y ofrece solo lo que falta. Antes de instalar, confirma los comandos exactos y las versiones, que toma de la documentación oficial compatibles con el manifiesto. Instala solo dependencias de desarrollo, no toca .env ni el código de la aplicación, y deja el job de CI como fragmento en el informe.

    Por último crea una prueba semilla por tipo sobre código que ya existe, la ejecuta y registra los comandos en la ficha y en development.md. La semilla no está solo para comprobar la instalación. Las reglas de pruebas entran al leer un fichero de prueba, y en un proyecto nuevo no había ninguno de React: a partir de ahora, la primera prueba del escenario tiene un vecino que leer.

    | Pruebas habituales | Backend: php artisan test · Vistas: npm test |
Fase 1

Arranque de la sesión

cada sesión

Antes de que nadie escriba nada, el harness decide qué entra en la ventana de contexto. Esta fase explica por qué la plantilla reparte la información entre varios documentos en lugar de concentrarla en uno.

  1. 01
    Harness

    Cargar el punto de entrada

    Lee CLAUDE.md, que importa AGENTS.md. Es una carga mecánica: el harness no entiende el contenido, solo lo inyecta. Por eso la ficha vive ahí —es el único archivo que todas las herramientas cargan siempre—.

  2. 02
    Harness

    Registrar herramientas, permisos, reglas y servidores

    Aplica las reglas de deny y ask de .claude/settings.json, detecta el .mcp.json versionado y registra las skills y los subagentes revisores disponibles. De los subagentes revisores solo carga una descripción de unas treinta palabras, para saber que existen. Las reglas de .claude/rules/ quedan a la espera: cada una indica en su cabecera paths: qué ficheros la activan, y ninguno se ha abierto todavía.

    Un servidor MCP de proyecto no se activa solo: queda como ⏸ Pending approval hasta que alguien lo apruebe, una vez.

    Excepción importante

    En ejecuciones desatendidas —claude -p, Agent SDK, sesiones en la nube— el harness no puede mostrar ese diálogo y carga los servidores de proyecto sin preguntar. El único apagado fiable es "disabledMcpjsonServers": ["shadcn"], que tiene precedencia sobre cualquier activación.

Qué hay en la ventana al terminar la fase 1

AGENTS.md — ficha y reglas generalesCargado
Descripción de skills y subagentes revisoresDeclaradas
Reglas de .claude/rules/A la espera de un fichero
.ai/project/development.mdNo leído

La diferencia entre declarado y cargado es la idea central de toda la plantilla. Ni el MCP, ni las skills, ni las reglas añaden contexto al arrancar: añaden la capacidad de ir a buscarlo cuando haga falta.

Fase 2

Encuadre de la petición

cada tarea

Llega la petición: «añade un formulario de alta de clientes: nombre y email, solo para gestores». No menciona dónde va el código, cómo se prueba, ni si hay que escribir una especificación. No debería tener que hacerlo.

  1. 01
    Agente principal

    Leer la ficha, que ya está en contexto

    Sin abrir ningún fichero, el agente principal ya sabe que el backend vive en app/ y las vistas en resources/js/, que se unen por una API REST, que las pruebas se lanzan con php artisan test y npm test, que hay un catálogo de componentes y que el proyecto trabaja con OpenSpec.

  2. 02
    Agente principal

    Clasificar la tarea

    Un alta de clientes introduce comportamiento nuevo en las dos capas: un endpoint que guarda datos y una pantalla que lo usa. No es trivial. Con la fila Especificaciones resuelta, el agente principal sabe que el comportamiento esperado se acuerda antes de escribir código.

    Corregir una errata en un texto, en cambio, saltaría directamente a la implementación. La plantilla no obliga a especificar lo que no lo necesita.

  3. 03
    Agente principal

    Comprobar si ya existe un cambio relacionado

    Si en openspec/ hubiera un cambio inequívocamente relacionado, el agente principal seguiría ese. No lee todas las especificaciones ni el histórico: es una regla explícita de AGENTS.md.

Fase 3

Especificación del cambio

si la tarea no es trivial

A partir de aquí manda OpenSpec. AGENTS.md dice cuándo entrar en este flujo y el workflow que OpenSpec instaló dice cómo recorrerlo. La plantilla solo añade una cosa: el orden de las pruebas.

  1. 01
    Agente principal OpenSpec

    Proponer el cambio

    El agente principal abre una propuesta con los comandos que OpenSpec instaló. El trabajo se parte en documentos separados dentro de una carpeta de cambio.

    /opsx:propose alta de clientes con nombre y email, solo gestores crea openspec/changes/alta-cliente/ ├─ proposal.md qué se quiere y por qué ├─ specs/ comportamiento esperado: los escenarios ├─ design.md decisiones técnicas: endpoint, tabla, pantalla └─ tasks.md plan de trabajo, una tarea por escenario

    Los escenarios son el corazón del cambio. Cada uno describe un caso que cualquiera del equipo puede leer, sin saber programar:

  2. 02
    Usuario

    Revisar la especificación — el punto de control real

    Este es el momento que justifica toda la fase. Corregir aquí un malentendido cuesta una frase; corregirlo después de implementar cuesta una tarde. ¿Falta el teléfono? ¿Un email con mayúsculas cuenta como duplicado? Se decide ahora, sobre texto legible, no sobre un diff.

    Si la petición y la especificación discrepan, o si la especificación contradice lo que el código ya hace, el agente principal debe señalar la diferencia y resolverla con evidencia antes de continuar, no elegir en silencio.

  3. 03
    Agente principal OpenSpec

    El plan: una tarea por escenario, prueba primero

    Al generar tasks.md, OpenSpec entrega al agente principal las rules de config.yaml. Por eso cada tarea nombra su escenario y empieza por su prueba.

Sobre estos comandos

Los nombres de los comandos y la estructura de la carpeta los define la versión de OpenSpec instalada, no este documento. Compruébalos en el workflow que dejó en el repositorio antes de darlos por fijos.

Fase 4

Implementación: las reglas de cada lenguaje

cada fichero

Con /opsx:apply alta-cliente empieza la implementación. Antes de ver el código conviene entender una pieza que actúa en segundo plano todo el tiempo: las reglas de .claude/rules/.

Cómo entra una regla en la ventana

1 · El agente principal lee un fichero app/Http/Controllers/ClienteController.php
→
2 · El harness compara la ruta con el paths: de cada regla: **/*.php coincide; **/*.{js,jsx,ts,tsx} no.
→
3 · Carga las que coinciden las comunes y las de PHP. Las de React siguen fuera. Nadie tuvo que pedirlas.

Cada regla es una hoja corta, de uno o dos kilobytes, con la cabecera que dice cuándo entra. Por ejemplo, la de seguridad de PHP:

Qué reglas carga cada fichero de este cambio

Reglas cargadas según el fichero abierto

openspec/changes/…/spec.md Ninguna No es código
  • Cada regla entra solo cuando hace falta. Las de pruebas, con ficheros de prueba; la seguridad común, solo con backend; las de Oracle, solo en proyectos con Oracle. Corregir un controlador no carga nada de pruebas.
  • Entran al leer, no al crear. Si el agente principal escribiera un fichero nuevo sin haber leído antes ninguno de su tipo, sus reglas no entrarían. Por eso development.md le pide leer un fichero vecino del mismo tipo antes de crear uno.
  • Las reglas de React entran con cualquier .js o .ts, también con ficheros de configuración como vite.config.js. El coste es pequeño y las rutas no permiten excluir carpetas.
  • Lo que depende de una acción, y no de un fichero, va en skills. Crear un endpoint, cambiar la seguridad o desplegar no se deduce del nombre de un fichero. Por eso la regla lleva una línea del tipo «al crear un endpoint, lee antes api-design», y la guía larga solo entra en ese momento.
  • Leer un documento no activa nada. Abrir la especificación o development.md no carga reglas de código.
  • Una vez dentro, se quedan hasta compactar. Las reglas no se descargan al cambiar de fichero: si en la misma sesión el agente principal pasa de PHP a React, la ventana acaba con las dos. Solo salen al terminar la sesión o al compactar la conversación con /compact, y vuelven a entrar al leer otro fichero que coincida. Si backend y frontend se hacen en sesiones distintas, cada una carga solo lo suyo. /context muestra qué reglas hay cargadas en cada momento.
Por qué no cargarlo todo siempre

Las reglas de la plantilla juntas ocupan unos 5.800 tokens. Sin paths:, estarían en todas las sesiones, incluidas las de Java en un proyecto que no tiene Java, o una conversación que solo pregunta por la arquitectura. Con paths:, corregir un controlador PHP carga unos 2.100; si además se tocan pruebas, unos 2.800; y una sesión que no toca código, cero.

Solo en Claude Code

Codex no tiene reglas por ruta. Allí el agente principal solo recibe lo que queda en development.md: comandos y convenciones propias del proyecto.

Fase 4

Backend: Laravel con pruebas primero

tareas 1.1 a 1.3

El backend recibe el formulario, lo valida, comprueba que quien lo envía es gestor y guarda el cliente en la base de datos. Cada una de esas responsabilidades nace de un escenario, y cada escenario pasa por el mismo ciclo de tres tiempos:

1 · Rojo

Se escribe la prueba del escenario y se ejecuta. Tiene que fallar, y por el motivo esperado: lo que falta es el comportamiento, no una coma.

2 · Verde

Se escribe el mínimo código que hace pasar esa prueba. Nada de adelantar escenarios que aún no tienen prueba.

3 · Ordenar

Con todo en verde, se limpia el código o la prueba sin cambiar lo que hacen, y se vuelve a ejecutar para confirmarlo.

Este orden lo impone operations.apply de openspec/config.yaml: OpenSpec se lo entrega al agente principal al empezar el apply, así que no depende de que alguien se acuerde de pedirlo.

  1. 01
    Agente principal

    Abrir solo lo pertinente

    La tabla «Contexto necesario» de AGENTS.md envía a .ai/project/development.md para implementar: comandos, el formato de la API del proyecto y sus convenciones propias. architecture.md no se abre porque la tarea no toca la arquitectura.

    Después lee el código vecino: routes/api.php y un controlador existente. La regla común lo pide («lee el código afectado antes de cambiarlo»), y es justo esa lectura la que hace entrar las reglas de PHP. Como va a crear un endpoint, la regla php/patrones.md le indica leer antes la skill api-design: así sabe que un alta responde 201 y un error de validación, 422.

    Antes de escribir la primera prueba, la guía de apply le pide leer una prueba existente del mismo tipo. Es la lectura que hace entrar las reglas de pruebas, que ya no vienen con cualquier fichero PHP.

  2. 02
    Agente principal

    Escenario «Alta correcta»: rojo

    La prueba traduce el escenario a código. El nombre del escenario va en #[TestDox]: así cualquiera, y más tarde el subagente revisor, puede emparejar escenario y prueba con una búsqueda.

    El agente principal la ejecuta sola, antes de escribir nada más:

    $ php artisan test --filter=AltaClienteTest FAIL Tests\Feature\AltaClienteTest ⨯ Alta correcta Expected response status code [201] but received 404. Tests: 1 failed

    Un 404 significa «esa dirección no existe»: es exactamente lo que falta. Es un fallo por el motivo esperado. Si hubiera fallado por un error de sintaxis o porque falta una clase de la prueba, no valdría: habría que arreglarlo hasta que el único motivo del fallo sea el comportamiento pendiente.

  3. 03
    Agente principal

    Escenario «Alta correcta»: verde

    Ahora sí, el mínimo código para que pase. Las reglas de PHP ya están en la ventana y marcan cómo escribirlo:

    Completan el verde la ruta en routes/api.php (protegida con auth:sanctum), la migración de la tabla clientes con índice único en el email, el modelo Cliente con su $fillable y el recurso ClienteResource.

    Lo que hace el códigoQuién lo pidió
    Controlador de tres líneas que delega la validación, sin servicio ni acciónphp/patrones.md: controladores delgados con FormRequest; un alta sin reglas de negocio puede quedarse en el controlador. Si el alta tuviera reglas propias, irían en una acción AltaCliente
    Responde con ClienteResource, no con el modelophp/patrones.md: respuestas con JsonResource
    Crea con validated() y el modelo declara $fillablephp/seguridad.md: evitar la asignación masiva
    Responde 201 en /api/v1/clientesSkill api-design y sección «API» de development.md
    Nombres en español y en PascalCase, sin dd()php/estilo-codigo.md
    $ php artisan test --filter=AltaClienteTest PASS Tests\Feature\AltaClienteTest ✓ Alta correcta 0.18s Tests: 1 passed
  4. 04
    Agente principal

    Ordenar

    Los siguientes escenarios van a repetir los mismos datos de ejemplo, así que el agente principal los saca a un método de la prueba. No cambia lo que se comprueba; solo cómo se escribe. Vuelve a ejecutar: sigue en verde.

  5. 05
    Agente principal

    Los otros dos escenarios, con el mismo ciclo

    EscenarioRojo: la prueba falla con…Verde: el mínimo cambio
    Email duplicado Expected 422 but received 500. El índice único de la base de datos rechaza el duplicado, pero con un error interno en lugar de un aviso al usuario. Añadir unique:clientes,email a la validación. Ahora responde 422 con el error en el campo.
    Usuario sin permiso Expected 403 but received 201. Cualquiera autenticado puede dar de alta. ClientePolicy::create que exige el rol gestor, y authorize() en el FormRequest que la usa.

    Fíjate en el primer rojo: sin la prueba, el duplicado habría llegado a producción como un error 500. El escenario lo destapó antes de escribir la solución.

Fase 4

Frontend: el formulario en React

tarea 2.1

El frontend es la pantalla que ve el gestor. No guarda nada por sí mismo: envía los datos al endpoint que acabamos de construir y muestra lo que responde. Así debe quedar:

  1. 01
    Agente principal Harness

    Abrir un fichero de React: entran sus reglas

    El agente principal lee un formulario existente en resources/js/. Es un .tsx, así que el harness añade las cuatro reglas de react/. Las de PHP no se van: siguen ahí de la parte anterior.

  2. 02
    Agente principal

    Consultar el catálogo en lugar de la memoria

    La sección «Sistema de diseño» de development.md le obliga a buscar en el catálogo antes de crear un componente, a no reimplementar uno que ya existe y a no deducir su uso si el servidor no responde. Así evita el fallo más común: escribir de memoria propiedades que ya no existen.

    → mcp__shadcn__search_items_in_registries registries: ["@shadcn"], query: "form input label button" ← devuelve form · input · label · button → mcp__shadcn__get_item_examples_from_registries query: "form field with error message" ← devuelve el ejemplo vigente, con su uso real
  3. 03
    Agente principal

    Rojo: la prueba del escenario, antes que el formulario

    Primero lee la prueba de otro formulario, lo que hace entrar react/pruebas. Luego crea un componente vacío que solo pinta los campos, para que la prueba pueda arrancar: si fallara porque el componente no existe, el motivo no sería el esperado. Después escribe la prueba, que simula la respuesta del servidor sin llamar a nada real:

    $ npx vitest run resources/js/clientes/AltaClienteForm.test.tsx FAIL AltaClienteForm > Error del servidor junto al campo Unable to find an element with the text: Ya existe un cliente con ese email. Tests 1 failed

    Falla porque el formulario aún no muestra errores: el motivo esperado. La prueba busca los elementos como lo haría una persona —por su etiqueta y su texto—, no por detalles internos del código.

    Harness Usuario

    Filtrar lo que escribe en disco

    Instalar un componente del catálogo toca ficheros. El harness aplica .claude/settings.json: lo que escribe o ejecuta puede pedir confirmación, y si la operación rozara un .env o una clave, la regla de deny la detiene antes de que el agente principal la vea.

  6. 06
    Agente principal

    Cerrar el apply con las pruebas del área

    Última tarea del plan: ejecutar las pruebas de las dos partes con los comandos de la ficha, no con unos adivinados. El resultado se guarda para la verificación y para los subagentes revisores, que así no tendrán que repetirlas.

Fase 5

Cierre del ciclo y revisión

cada cambio

Quedan seis pasos, y ninguno ocurre por iniciativa del agente principal: los comandos los lanza el usuario, y los subagentes revisores solo se ejecutan si el usuario dice que sí.

  1. 01
    Usuario OpenSpec

    Verificar el cambio

    OpenSpec contrasta la implementación con el cambio: tareas completas, requisitos cubiertos y escenarios con prueba. Solo informa; no corrige nada ni impide archivar.

    /opsx:verify alta-cliente ✓ 5/5 tareas completas ✓ 4/4 escenarios con prueba asociada ✓ Diseño reflejado en el código
  2. 02
    Agente principal Usuario

    La pregunta: ¿pasamos subagentes revisores?

    Tras verificar, el agente principal no lanza nada por su cuenta. Propone los subagentes revisores que encajan con lo que se ha tocado y pregunta:

    Pregunta del agente principal

    El cambio alta-cliente está verificado. ¿Quieres pasar algún subagente revisor antes de archivar?

    • php-reviewer, react-reviewer y security-reviewer El cambio toca Laravel, React y un endpoint que recibe datos del usuario
    • Solo algunos, o sobre otra parte Por ejemplo, solo el backend, o solo app/Http/
    • No, seguir sin revisar No se lanza ningún subagente revisor
    Si lo activas

    Se lanzan en paralelo, cada uno con su ventana

    Cada subagente revisor es otro agente que empieza de cero: no ve la conversación ni el razonamiento del agente principal, solo el resultado. Por eso sirve de segunda opinión.

    Solo leen e informan. No cambian ni una línea: las correcciones las hace la conversación principal cuando tú lo decides.

    Si no lo activas

    No se ejecuta nada

    Ningún subagente revisor lee el código ni consume tiempo. El agente principal no los lanza por su cuenta aunque crea que convendría.

    Al archivar, la guía de archive de config.yaml lo recuerda una vez si nadie los ofreció tras verificar. Si vuelves a decir que no, se archiva sin revisión. También puedes pedirlos en cualquier momento: «revisa app/Http con php-reviewer».

    Los otros dos informan de un aviso medio cada uno: el botón no se desactiva mientras se envía, lo que permite un doble clic, y el endpoint de alta no tiene límite de frecuencia.

  4. 04
    Agente principal Usuario

    Corregir lo que bloquea y decidir el resto

    La conversación principal corrige el alto: añade la comprobación que faltaba y ejecuta la prueba, que sigue en verde. Los medios se te presentan para que decidas: el doble clic se corrige ahora; el límite de frecuencia se deja anotado como pendiente. Puedes volver a pasar el subagente revisor sobre la corrección si quieres confirmarla.

    La regla es la de development.md: los hallazgos críticos y altos se corrigen antes de entregar, o se explica por qué no.

  1. 05
    Usuario OpenSpec

    Archivar el cambio

    Con la implementación completa, el cambio se archiva y su carpeta pasa al histórico. Lo que era comportamiento propuesto queda consolidado como comportamiento vigente.

    /opsx:archive alta-cliente mueve openspec/changes/alta-cliente/ → openspec/changes/archive/alta-cliente/

    Antes de mover la carpeta, OpenSpec entrega al agente principal la guía de archive de config.yaml: si nadie ofreció los subagentes revisores, pregunta una vez; y no se archiva con hallazgos críticos o altos abiertos salvo que el usuario lo acepte de forma explícita. Los detalles temporales del cambio se quedan en el histórico; no se copian a .ai/project/, que documenta lo estable.

  2. 06
    Agente principal

    Rendir cuentas

    Antes de proponer nada, el agente principal revisa el diff final, elimina restos y repite las comprobaciones si el árbol cambió después de validarlo. Informa de qué cambió, qué comprobó y qué queda pendiente —aquí, el límite de frecuencia—. Hasta aquí, nada se ha versionado.

El commit, paso a paso

La skill commit es un buen retrato de cómo funciona cualquier procedimiento de la plantilla, así que merece verse entera. Solo se invoca cuando el usuario lo pide de forma explícita: pedir un commit no autoriza a hacer push, publicar ni desplegar.

  1. 01
    Usuario commit

    Preparación

    Revisa el estado, el resumen de cambios y el historial reciente —para adoptar las convenciones del repositorio, no las suyas—. Examina el diff evitando volcar binarios completos.

    Busca secretos, credenciales, datos personales y artefactos que no deban versionarse. Si aparece alguno, detiene su inclusión e informa.

  2. 02
    commit

    Staging explícito

    Añade las rutas una a una. Nada de git add . ni -A sin haber verificado antes todo su alcance: el objetivo es que ningún cambio ajeno entre por arrastre.

    git add app/Http/Controllers/ClienteController.php tests/Feature/AltaClienteTest.php ... git status --short ¿falta o sobra algo? git diff --cached ¿es esto lo que creo? git diff --cached --check errores de espacios en blanco
  3. 03
    commit

    El mensaje

    Conventional Commits, salvo que el repositorio documente otra convención. Tipo elegido por el propósito principal del cambio, resumen concreto sin punto final y en el idioma del proyecto: por ejemplo, feat(clientes): añade el alta de clientes. Cuerpo cuando haya algo que explicar: efectos, migraciones o relación con una especificación.

    Sin trailers de autoría, modelo o herramienta, salvo que el repositorio los exija. Si el mensaje lleva cuerpo o caracteres delicados para el shell, se escribe en UTF-8 y se pasa con git commit -F.

  4. 04
    commit

    Verificación y límites

    Después del commit comprueba qué ha quedado pendiente, relee el mensaje creado e informa de lo que se dejó fuera deliberadamente.

    Lo que la skill no hace nunca: commits vacíos, push, --amend o --no-verify sin petición explícita, desactivar hooks para que el commit termine, o reescribir historial por iniciativa propia. Si un hook falla, primero comprueba si el commit llegó a crearse.

El ask sobre git push en los permisos es la segunda red: aunque el procedimiento se saltara su propio límite, el harness seguiría preguntando.

§

El mismo ciclo, otras decisiones

Buena parte del recorrido depende de lo que se decidió en la fase 0. Dos proyectos con la misma plantilla se comportan de forma distinta sin que nadie apague nada a mano.

Según la fila «Especificaciones»

OpenSpec instalado

Con escenarios y pruebas primero

Las tareas no triviales pasan por propuesta, revisión, apply con pruebas primero, verificación y archivado. El comportamiento esperado se acuerda por escrito antes de tocar código.

No se usa

Sin fase 3

El ciclo salta del encuadre a la implementación y la petición hace de especificación. Las reglas por lenguaje siguen actuando igual, y los subagentes revisores se ofrecen tras un cambio grande o en una parte crítica.

Según cómo se unen Laravel y React

API REST + SPA

El recorrido de este documento

Laravel expone endpoints JSON y React los consume. Hay un contrato que mantener entre las dos partes, así que se conservan las skills api-design y contract-first.

Inertia.js

Sin API intermedia

El controlador pasa los datos directamente a la página React, sin endpoint JSON. Las pruebas del backend comprueban la página que se renderiza, y la skill contract-first se retira en la adopción porque no hay contrato que versionar.

Según la fila «Sistema de diseño»

react18 · laravel10

Con catálogo

Ambos declaran context.mcp. En Laravel el catálogo aplica a las vistas React de resources/js/; Blade queda solo como plantilla raíz.

springboot3 · springboot4

Sin catálogo

No declaran la clave, así que no se genera .mcp.json: no hay servidor que aprobar ni configuración que apagar.

El apagado no depende de que nadie se olvide de una clave: depende de que la clave no exista. Es la diferencia entre una protección y una convención.

Pendiente de comprobar

Algunos puntos de este recorrido no están verificados contra las herramientas reales: si Codex aplica una aprobación equivalente a los mcp_servers de .codex/config.toml; el comportamiento en monorepos, donde .mcp.json es de raíz y no admite alcance por subdirectorio; y los nombres exactos de los comandos de OpenSpec, que dependen de la versión instalada.

Sí está comprobado en la documentación de Claude Code que las reglas por ruta entran al leer un fichero y no al crearlo, que salen de la ventana al compactar y que paths: admite llaves también en carpetas. Para confirmarlo en un proyecto concreto, /context muestra las reglas cargadas y el hook InstructionsLoaded registra cuándo entra cada una.

Además, el sandbox de Codex fija network_access = false, que bloqueará tanto la instalación de OpenSpec como npx shadcn mientras no se apruebe la salida.

Documento interno de la plantilla aiconventions. El ejemplo de código es ilustrativo y está abreviado. Los comandos de OpenSpec y los nombres de las herramientas MCP los publica cada herramienta: compruébalos en el repositorio y con /mcp antes de darlos por fijos.
